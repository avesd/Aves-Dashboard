## Findings

### AUDIT-001 - Failed replacements exhaust mount capacity and prevent repair

**Class:** `defect`

**Severity:** P2

**Confidence:** High

**Area:** Canvas renderer/host lease lifecycle and recovery.

**Reachability:** Ordinary source initialization failures. A supported 64-block canvas needs only one failed replacement per block, submitted in bounded batches; no race is required.

**Blast radius:** One canvas window's ability to display subsequent source versions.

**Reversibility:** Closing and reopening the window releases the leases. Saved source/data is not lost; ordinary repair and repeated synchronization do not recover the exhausted window.

**Documented trade-off:** [Dashboard blocks:47](../../../docs/dashboard-blocks.md#L47) intentionally preserves the previous display on failure and permits 64 blocks. [Replacement behavior:128](../../../docs/dashboard-blocks.md#L128) keeps unrelated roots alive.

**Decision status:** `drift`

**Why this finding is outside the accepted boundary:** Retaining the displayed version is intentional; retaining obsolete failed candidates until they prevent the next repaired version from mounting is not required by that behavior.

**Evidence:**

- [sandbox-messages.ts:52](../../../packages-renderer/canvas/src/blocks/sandbox-messages.ts#L52): only `ready` releases older versions; `error` retains them.
- [block-runtime.ts:330](../../../apps/desktop/src/main/canvas/blocks/block-runtime.ts#L330): 128 leases for one owner prevent further mounts.
- [block-runtime.ts:292](../../../apps/desktop/src/main/canvas/blocks/block-runtime.ts#L292) and [error reporting:366](../../../apps/desktop/src/main/canvas/blocks/block-runtime.ts#L366): snapshots skip obsolete leases and error reports do not reclaim them.
- [canvas-sandbox.ts:195](../../../packages-renderer/canvas/src/blocks/canvas-sandbox.ts#L195) and [catch:244](../../../packages-renderer/canvas/src/blocks/canvas-sandbox.ts#L244): `requested` is set before mount succeeds and is not rolled back on rejection.

**Observed behavior:** A reproduction using the real renderer coordinator and host runtime mounted 64 ready blocks, then failed replacements in two groups of 32. It recorded 64 error reports and zero releases. A valid revision-3 repair was rejected at capacity, reported `unmounted`, and continued displaying revision 1. Synchronizing the same repair again attempted zero mounts.

**Impact:** A normal source-repair workflow becomes stuck until the user reopens the canvas. Error status for the newly saved repair is also reduced to `unmounted`.

**Missing or inadequate verification:** Existing canvas integration tests cover owner destruction and action/storage boundaries, but not renderer-driven failed replacement and capacity recovery. The reproduction substitutes native protocol registration and iframe responses; it is not native visual verification.

**Minimum sufficient remediation:** Reclaim superseded failed candidates before mounting another source version, retaining the displayed version and necessary current error diagnostics. Complete release before relying on reclaimed capacity. Undo the pending `requested` marker when mount fails so the same version can retry. Raising the limit alone does not fix the lifecycle.

**Verification scope:** Cover 64-block failed replacement followed by repair, preservation of the old display, and same-version retry after capacity becomes available. Run affected renderer/desktop checks and a focused native replacement scenario when implementing.

### AUDIT-002 - Data-only updates invalidate the independent canvas revision

**Class:** `defect`

**Severity:** P3

**Confidence:** High

**Area:** Canvas mutation revision semantics.

**Reachability:** A normal Agent render request supplies only block data plus `expectedDataRevision`, followed by a source/layout edit based on the previously read canvas revision. Fully sequential operations reproduce it.

**Blast radius:** Pending edits to that canvas, including unrelated blocks.

**Reversibility:** Reread the canvas and issue a reconsidered command with a new request ID. No persisted content is lost.

**Documented trade-off:** [Dashboard blocks:95](../../../docs/dashboard-blocks.md#L95) explicitly states that data/view-state revisions do not increment the canvas/source revision. [Canvas service:23](../../../docs/canvas-service.md#L23) separates source/layout changes from data changes.

**Decision status:** `drift`

**Why this finding is outside the accepted boundary:** The independent data revision is already checked, but every render additionally increments the canvas revision, creating a conflict for an unchanged source/layout state.

**Evidence:**

- [canvas-service.ts:253](../../../apps/desktop/src/main/canvas/canvas-service.ts#L253): all renders compare `expectedRevision`.
- [canvas-service.ts:280](../../../apps/desktop/src/main/canvas/canvas-service.ts#L280): every render unconditionally writes `state.revision + 1`.
- [dashboard-blocks.ts:377](../../../packages/workspace-model/src/canvas/dashboard-blocks.ts#L377): data revisions and source revisions are already updated independently in the model.

**Observed behavior:** Using real `WorkspaceFile` and `CanvasService` with temporary synthetic storage, a data-only update changed canvas/source/data revisions from `1/1/0` to `2/1/1`. A subsequent source edit with expected canvas revision 1 returned `REVISION_CONFLICT` even though source/layout had not changed.

**Impact:** Unnecessary rejected edits and rereads; low-impact but directly contrary to the adopted revision contract.

**Missing or inadequate verification:** Current targeted canvas tests exercise host data actions, not the service's data-only render revision behavior.

**Minimum sufficient remediation:** Classify render changes by whether they affect canvas-level structure/metadata. Preserve the canvas revision for a strictly data-only batch while keeping independent data checks, atomic receipts, and change notifications. Mixed batches still increment the canvas revision once.

**Verification scope:** Real-service tests for pure data updates, mixed data/source edits, unchanged-revision source edits after data writes, stale data rejection, and identical receipt retries; affected desktop/model checks.

### AUDIT-003 - Initial script failure leaves an orphaned error placeholder

**Class:** `defect`

**Severity:** P3

**Confidence:** High

**Area:** Generated canvas document DOM lifecycle.

**Reachability:** A block's first source throws during initialization, a later source succeeds, then the block is removed. No concurrency is necessary.

**Blast radius:** Error placeholder DOM for the affected block in its open canvas.

**Reversibility:** Reopening the canvas rebuilds the document. Source/data remains intact.

**Documented trade-off:** [Dashboard blocks:35](../../../docs/dashboard-blocks.md#L35) defines full source replacement and removal releasing the displayed document. Preserving a previous successful display does not justify retaining an unowned initial-error placeholder.

**Decision status:** `drift`

**Evidence:**

- [canvas-document.ts:86](../../../apps/desktop/src/main/canvas/canvas-document.ts#L86): the new slot carries only `previous.displayed` and its candidate, dropping `previous.errorHost`.
- [canvas-document.ts:151](../../../apps/desktop/src/main/canvas/canvas-document.ts#L151): failed initial source adds `slot.errorHost`; later success tries to remove it from the newly created slot.
- [canvas-document.ts:185](../../../apps/desktop/src/main/canvas/canvas-document.ts#L185): removal can clean only the current slot's references.

**Why this finding is outside the accepted boundary:** The old placeholder becomes unreachable from lifecycle state, so repair and removal cannot release all of that block's visible nodes.

**Observed behavior:** A synthetic page running the real `canvasDocument()` in headless Chrome produced `#world > .block` counts of 1 after initial failure, 2 after successful repair, and 1 after removal. No screenshots or real product data were used. The lead independently reopened the ownership and cleanup branches.

**Impact:** A stale error placeholder remains after the actual block is repaired or deleted; repeated failures can accumulate nodes.

**Missing or inadequate verification:** No existing failure-to-repair-to-remove DOM regression covers this path. Headless Chrome establishes DOM cleanup behavior, not complete Electron presentation.

**Minimum sufficient remediation:** Explicitly transfer or remove `previous.errorHost` when replacing a slot, and ensure success, repeated initial failure, and removal each leave only the appropriate current host.

**Verification scope:** A focused DOM lifecycle test for fail → repair → remove and repeated initial failures, plus affected checks and focused visual verification during remediation.

### AUDIT-004 - Known history-limit errors become generic retry failures

**Class:** `defect`

**Severity:** P3

**Confidence:** High

**Area:** DeepSeek host → session execution → IPC operational errors.

**Reachability:** Normal accumulated conversation history exceeds the existing bound; no provider failure or race is required.

**Blast radius:** Error diagnosis and recovery guidance for one conversation.

**Reversibility:** Starting a new conversation restores operation. Retrying in the same conversation does not shrink history.

**Documented trade-off:** [Agent sessions:64](../../../docs/agent-sessions.md#L64) accepts bounded history and no automatic retries. [AGENTS.md:67](../../../AGENTS.md#L67) requires preserving safe operational codes and details while sanitizing unknown failures.

**Decision status:** `drift`

**Evidence:**

- [deepseek-agent-host.ts:190](../../../apps/desktop/src/main/agent/deepseek-agent-host.ts#L190): throws `BUSY` with specific new-conversation guidance.
- [deepseek-agent-host.ts:337](../../../apps/desktop/src/main/agent/deepseek-agent-host.ts#L337): discards the caught error and throws a plain `Error`.
- [session-execution.ts:101](../../../apps/desktop/src/main/agent/sessions/session-execution.ts#L101): preserves known operational errors but must turn the replacement plain error into `INTERNAL` with “Please try again.”

**Why this finding is outside the accepted boundary:** The history bound is valid; destroying its known safe failure classification is not required by that bound or by unknown-error sanitization.

**Observed behavior:** Real host/session/IPC classes with synthetic fetch accepted five legal 32k prompts. The sixth hit the history limit and returned `INTERNAL / Agent task failed. Please try again.` A seventh short retry returned the same failure; provider request count remained five. The emitted status event does mention a possible conversation limit, but mixes it with configuration/quota causes instead of preserving the known cause.

**Impact:** Misleading retry guidance and avoidable troubleshooting for a condition that requires a new conversation. No data loss or extra provider request was observed in the reproduction.

**Missing or inadequate verification:** Existing provider/session tests do not carry a real host history-limit error through the session and IPC layers.

**Minimum sufficient remediation:** Catch the actual error, keep pending-tool history repair, and preserve known `OperationError` codes and safe messages in both status and rejection. Continue sanitizing unknown failures; retain the history limit.

**Verification scope:** A host → sessions → IPC regression for exhausted history and a separate unknown-error case; affected Agent tests and desktop checks.
